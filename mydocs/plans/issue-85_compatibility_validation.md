# G11-01 전체 호환성·성능 검증 계획

이슈: [#85](https://github.com/edwardkim/ohmylemmings/issues/85) · 상위 [#1](https://github.com/edwardkim/ohmylemmings/issues/1) · [전체 계획](issue-1_implementation_plan.md).

기준 main은 `7b64dad34d90fa27249b9d76a6339dd1faed3aa2`다. G00~G10의 기능별 검증을 바탕으로 G11의 전수 실행과 측정 절차를 정한다. 이번 절편은 계획·소스 점검·증거 색인으로 한정한다. 제품 코드 변경, 새로운 런타임 통과 판정과 성능 측정은 없다.

## 범위와 판정

[기존 호환성 계약](../tech_insights/issue-5_compatibility_baseline.md)의 DOS Original VGA/AdLib, 4난이도×30레벨, 8직업, 21곡, 18효과음, COMP-01~18을 유지한다. Oh No/Holiday·CGA/Tandy·사용자 레벨은 범위 밖이다. 원본 식별과 고정 레퍼런스는 [dos_original.json](../../assets/manifests/dos_original.json)·[reference_sources.json](../../assets/manifests/reference_sources.json)을 사용한다. 원본과 전체 실행 자료는 ignored `assets/local/`에 두고 공개 자료에는 출처·수치·해시를 남긴다.

[120개 표](../tech_insights/issue-85_compatibility_matrix.md)와 [compatibility_plan.json](../../assets/manifests/compatibility_plan.json)에 레벨 ID·제목·DAT/부품·ODD·스타일/특수·기본 레코드 해시·지원 제한·기존 증거를 연결했다. 기계 목록은 8직업과 music-00~20, sfx-00~17, COMP-01~18도 전부 포함한다. 원본 오디오 raw ID는 각각 1~21, 1~18이며 자원 인덱스와 1 차이 난다. 곡 순서는 초기 기준 문서의 modulo-21 대신 [#78의 normal cursor·4개 special·retry 계약](../tech_insights/issue-78_game_sound.md)을 따른다.

| 판정 종류 | 의미와 사용 조건 |
| --- | --- |
| 소스 범위 내 | 정상 진입을 막는 아래 두 제한에 해당하지 않음. 실행이나 완주 통과는 아님 |

## 현재 증거와 확인한 차이

정적 자원 증거는 120개 전체를 포함한다. [#15 지형](../../assets/manifests/level_terrain.json)은 30,412,800픽셀과 팔레트, [#19 객체](../../assets/manifests/level_objects.json)는 preview/initial 240장면·60,825,600픽셀을 독립 구현과 대조했다. 동적 트리거/물리나 호스트 실행의 인증은 아니다.

[#60 네이티브](../reports/issue-60_native_playthrough.md)는 Fun01 성공·실패·재시작과 Fun02 진입 1,699상태, [#70 실제 Web](../reports/issue-70_web_playthrough.md)은 같은 범주의 원본 브라우저 1,695상태와 별도 재생을 검증했다. [#26](../../assets/manifests/state_replay.json)과 직업별 증거는 추출한 기준 함수·지원 상태에 한정한다. DOS 영상의 장면/숫자 일치는 DOS 내부 모든 상태 일치와 구분한다.

음향은 [#74](../../assets/manifests/adlib_stream.json)의 원본 x86 드라이버 21곡/18효과음·227,615호출, [#76](../../assets/manifests/adlib_pcm.json)의 고정 합성기 native/WASM·독립 C, [#78](../../assets/manifests/game_sound.json)의 사건/곡 순서, [#80](../../assets/manifests/audio_output.json)의 장치 수명과 활성화 증거를 재사용한다. [#82](../../assets/manifests/audio_playthrough.json)는 합성/원본 각각 580경계·1,824,750PCM, 일부 실제 DOS/SDL 출력과 사용자 청취 통과다. 물리 DAC 계측이나 전곡 DOS 파형 동일성으로 확대하지 않는다. 공개 증거 12개와 소스 10개의 크기/SHA-256을 목록에 고정했다.

## 전수 실행 계약

각 실행 묶음에 레벨 ID, 원본/빌드/실행 파일/입력 해시, 메커니즘 옵션, pacing, 정렬된 `(control_step, sequence)` 입력, 매 경계 정규화 상태·맵, 최종 승패/구출률, 기준 종류·지원 필드, 첫 차이와 산출물 해시를 기록한다. 코어 해시에서 벽시계·렌더 빈도를 제외하며 기존 trace 직렬화 규칙을 유지한다. 재시작은 새 run ID/세대·경계 0과 초기 맵/재고/음원 큐를 확인한다.

1. 120개 각각 실제 SDL과 실제 WASM에서 원본 로드·초기 수치·지형/강철/객체·팔레트·패널/카메라를 대조한다. 모든 진입점을 340 control steps까지 무입력 재생하고 중간 결과가 나면 결과 상태 고정을 확인한다. 340은 초기 점검 길이이며 완주 길이가 아니다.
2. COMP-17은 각 레벨의 유효한 원본 해법 성공·실패·재시작을 요구한다. 해법은 기록된 게임 입력으로 실제 재고/지형/구출 목표를 충족해야 한다. 목표 강제 변경·성공 상태 주입을 해법으로 계산하지 않는다. 실패 입력도 최종 사유와 숫자를 기록한다. 해법 미확보 레벨은 미검증으로 남긴다.
3. 같은 저장 입력을 플랫폼별 3회 반복하고 렌더 주기·시간 전달 분할을 바꿔 상태/맵/결과를 대조한다. 실제 브라우저 UI는 원시 포인터/키·캔버스를 확인하고 안정된 actor ID 재생과 구분한다. 기준 함수의 지원 필드, 고정 golden, 실제 DOS 영상/숫자, 사용자 관측을 증거 종류로 표시한다.
4. DOS 관측은 원본/에뮬레이터/설정/속도와 입력·영상 해시를 기록하고 대표 사례를 장면/결과로 비교한다. 해당 레벨에 DOS 증거가 없으면 그 차원은 미검증이다. native/WASM 일치만으로 원작 일치를 선언하지 않는다. G11 최종 보고에 이 한계를 명시한다.
5. 선택 난이도 경계 1/30·잘못된 ID, 손상/누락/중복 파일, 실패한 자원 교체 시 기존 세션 보존, 레벨/재시작/Continue의 음악 cursor와 큐 세대, 마지막 레벨의 전환을 포함한다. 난이도 끝의 원작 전환 의미는 G11-02에서 기준 소스/관측을 확인한 뒤 계약을 정한다.

## 성능 측정 계약

현재 성능 상태는 `unmeasured`다. 아래 반복 횟수와 기준은 후속 측정 절차이며 결과값이 아니다. G11-04/05의 입력/산출물 해시를 먼저 고정한다. 원본 전체 로드 120개, 표준 스타일5종·특수4종, 최대 동시 개체·직업/지형 변경이 많은 구간, Fun01 완주, 음악/효과음 단독 및 동시 발생의 재현 입력을 선정하고 ID·경계 길이·개체/변경량·샘플 수를 공개한다. 대표 구간만 측정하면 그 범위를 명시한다.

| 단계 | 측정 구간과 출력 |
| --- | --- |
| 파일 읽기 | 별도 신규 프로세스의 파일 open/read. OS cache 상태를 기록하고 무통제 첫 실행은 cold-cache로 부르지 않음 |
| 해제·장면 합성 | 이미 메모리에 있는 동일 바이트로 DAT 해제부터 완성 장면까지. 파일/다운로드/로그 저장 제외 |
| 틱 | 고정 초기 상태·입력·경계 수, 렌더/PCM/I/O 제외. ns/tick·states/s·최종 상태/맵 해시 |
| 렌더 | 고정 상태의 같은 장면·해상도·픽셀 형식. CPU 합성과 SDL 업로드/Canvas 전송을 분리, ns/frame·RGB 해시 |
| PCM | 장치 없이 같은 명령·시계·44100Hz mono와 고정 샘플 수/청크. ns/sample·samples/s·PCM 해시. 실제 장치 주파수도 별도 기록 |
| 실제 SDL/Web | release/WASM 최적화 빌드, 표시 화면·오디오 켬. 최소60초의 고정 부하/반복 재생, frame interval·틱 지연·오디오 queue/underrun·메모리. DOM/장치 정책과 숨김/재개 별도 |
| 검사/CI | 컴파일·링크·개별 검사·픽셀 캡처/파일 기록·의존성 준비 시간과 전체 벽시계. `--fast`/오디오 off 명시, 제품 프레임 속도와 분리 |

환경에는 source/binary/input SHA, OS/kernel/CPU·코어 수/메모리, 전원 모드·부하, Rust/Python/SDL/브라우저/드라이버 버전, 빌드 profile/flags, OS cache·프로세스/JIT 초기화 상태, 해상도/scale/vsync, pacing, 오디오 rate/채널/quantum과 장치/백엔드를 기록한다. CI는 runner·job·캐시 hit·명령/로그를 추가한다. 서로 다른 CI runner 시간만으로 제품 회귀를 판정하지 않는다.

알고리즘 측정은 동일 조건에서 준비 3회 후 측정 30회, monotonic clock과 고정 연산 수를 쓴다. 원시 표본·median·p95(nearest-rank, 정렬30개 중29번째)·max·처리량·peak memory를 남긴다. 장치 실시간은 호스트별60초 구간을3회 반복하고 틱/프레임/quantum 사건별 분포를 보고한다. CI는 조건이 맞는 기존3회 실행 로그와 개별 명령1회 계측을 먼저 이용하며 변동/병목 확인에 필요한 경우만 반복한다. 적은 CI 표본으로 p95를 추정하지 않는다. 반복마다 같은 상태를 재구성하고 초기화 시간을 별도 측정한다. 작은 구간은 여러 연산을 묶어 시계 비용보다 크게 만들고 그 횟수를 기록한다. 외부 다운로드·화면 덤프·해시 계산은 알고리즘 측정 구간 밖에 둔다.

알고리즘 비교는 같은 머신에서 baseline/candidate를 번갈아 30쌍 실행한다. median 또는 p95가 10%를 넘게 악화되면 동일 조건의 두 번째 묶음으로 재확인한다. 재현되면 회귀로 기록하고 최초 병목 프로파일·오차/표본 변동·원인을 조사한다. 실제 호스트는3쌍의 마감 지연/underrun·사건별 분포로 비교하며 CI는 별도 벽시계 자료로 다룬다. 차이가 변동 범위 안이면 추가 근거 없이 개선/회귀로 단정하지 않는다. 이 기준은 조사 기준이며 임의의 모든 장치 성능 보증은 아니다.

실시간 기본 예산은 [현재 pacing](../../crates/lemmings-session/src/pacing.rs)의 DOS `2190197/156250` updates/s, reference `17/1` updates/s와 선택 표시주기/장치 quantum에서 계산한다. 게임 초의 17회와 DOS 벽시계 속도는 다르다. 틱·렌더·PCM 개별 처리량 외에 실제 호스트에서 해당 마감 지연/underrun 0을 요구하고 측정 환경·부하를 같이 보고한다. 실행이 빠른 `--fast` 결과를 실시간 장치 통과로 계산하지 않는다.

최적화는 병목이 확인되고 목표 예산 미달/회귀가 재현될 때만 별도 이슈로 한다. 사전/사후 입력·상태·맵·동일 합성기 PCM 해시가 같아야 하며, 동작 변경이 필요하면 호환성 수정 이슈로 분리한다. SIMD·동시성 도입을 선결하지 않는다. 원본 기준 파일과 일치성 조건을 유지한 채 개선을 재측정한다.

# 분할정복 기반 전체 구현 계획

상위 추적 이슈: [GitHub #1 — 전체 구현 계획](https://github.com/edwardkim/ohmylemmings/issues/1).

## 목적과 현재 상태

[프로젝트 기획서](rusty_lemmings.md)의 원본 호환 Rust 엔진을 작고 검증 가능한 목표로 나눕니다. 데스크톱과 웹에서 기준판의 레벨·직업·게임 규칙·사운드를 재현하는 것이 최종 목표입니다.

현재는 문서 준비 단계입니다. 아래 G00~G12는 모두 대기 상태이며, 계획 작성과 실제 기능 구현의 진행 상태를 각각 추적합니다. 작업 순서는 주차보다 선행 조건과 완료 증거를 기준으로 정합니다.

## 분할 원칙

1. 파싱, 지형, 시뮬레이션, 게임 세션, 플랫폼 어댑터의 책임과 입력·출력을 분리합니다.
2. 각 목표를 한 종류의 동작이나 인터페이스를 검증하는 후속 작업으로 쪼갭니다. 목표 하나에 여러 구현 PR을 연결할 수 있습니다.
3. 합성 바이너리·지형·입력 시퀀스로 코어를 검증하고, 원본 리소스와 플랫폼은 통합 목표에서 연결합니다.
4. 선행 목표가 준비되면 독립적인 모듈을 진행할 수 있습니다. 공통 인터페이스 변경은 관련 계획과 의존 작업에 반영합니다.
5. 작은 단위에서 TDD를 적용하고, 관찰 가능한 동작을 구현할 때마다 실행 가능한 결과를 남깁니다.

G02~G03 리소스 처리와 G04~G05 코어 개발은 G01 이후 분리해 진행할 수 있습니다. G06에서 두 경로를 통합합니다. G07은 직업별로 세분화하며, G06 화면을 이용한 수동 확인과 자동 테스트를 함께 수행합니다.

## 초기 실행 순서

첫 착수 목표는 **G00**입니다. 아래 작업을 각각 하나의 후속 이슈로 처리할 수 있습니다.

1. **G00-01 기준판 식별:** 대상 DOS 버전, 리소스 파일 목록·식별값, 확보 여부를 기록합니다. 자료가 부족하면 부족한 항목과 확인 방법을 남깁니다.
2. **G00-02 레퍼런스 고정:** Lemmix·Lemmings.ts의 참고 버전·파일·함수와 분석할 영역을 기록합니다.
3. **G00-03 완료 기준 정의:** 지원할 전체 레벨·직업·규칙·사운드 목록, 틱 동작 확인 방법, 비교용 첫 레벨과 입력 시나리오를 정합니다. 미확정 항목은 해결 후 G00를 완료합니다.
4. **G01-01 개발 골격:** 코어·리소스·플랫폼 경계를 정의하고 최소 Cargo 구성과 테스트 한 개를 추가합니다.
5. **G01-02 개발 검증:** 포맷·린트·테스트·빌드 명령을 CI와 문서에 연결합니다.
6. **G02-01 / G04-01 독립 구현:** 첫 DAT 구간 읽기와 합성 픽셀 맵의 읽기·경계 검증을 별도 이슈로 진행합니다.

## 첫 번째 실행 결과와 확장 순서

- **G06:** 원본 지형 위에서 레밍이 이동하는 네이티브 화면
- **G08:** 직업 할당과 판정이 가능한 네이티브 한 레벨 완주
- **G09:** 같은 레벨과 입력을 재현하는 웹 실행
- **G12:** 전체 호환성 검증을 거친 데스크톱·웹 배포물

처음에는 작은 fixture와 기준 레벨 하나로 연결을 검증하고, 이후 G00의 전체 레벨·직업 목록으로 범위를 넓힙니다. SIMD·동시성 등 성능 변경은 G11의 측정 근거와 상태 일치 검증을 갖춘 후속 작업으로 분리합니다. 코어의 `no_std` 적용 범위도 실제 의존성과 검증 결과를 기록합니다.

## 후속 작업 이슈의 필수 항목

- 상위 추적 이슈와 목표 ID, 예: `G02-01 DAT 구간 읽기`
- 선행 작업과 착수 조건
- 이번 작업의 범위, 입력·출력, 예외·경계 조건
- 테스트 시나리오와 관찰 가능한 완료 기준
- 관련 `plans/`, `orders/`, `tech_insights/`, `feedbacks/` 문서
- `working/` 진행 기록과 `reports/` 검증 결과

직업 구현은 직업 한 종류를 기본 작업 단위로 삼고, 공통 지형 연산과 직업 간 상호작용 검증은 각각 별도 작업으로 나눕니다. 하나의 PR에 독립적인 여러 목표가 섞이면 작업을 더 분리합니다.

## 진행 상태와 완료 처리

이 계획에서는 `대기 → 준비 → 진행 → 검증 → 완료`로 상태를 기록합니다. 선행 조건이 충족되면 준비, 구현과 문서 갱신을 시작하면 진행으로 변경합니다. 막힌 항목에는 원인과 다음 행동을 기록합니다.

1. 작업 이슈와 `orders/`에 범위·검증 기준을 정리합니다.
2. `working/`에 현재 상태와 다음 행동을 남기며 TDD로 구현합니다.
3. `reports/`에 변경 내용, 실행한 검증 명령과 결과, 남은 한계를 기록합니다.
4. 완료 기준을 충족하면 후속 이슈를 완료하고, 해당 목표의 모든 작업이 끝나면 상위 이슈의 목표를 체크합니다.
5. 변경된 기술 지식과 피드백을 문서에 반영합니다. G00~G12 전체 기준을 충족하면 상위 이슈를 완료합니다.

# 분할정복 기반 전체 구현 계획

상위 추적 이슈: [GitHub #1 — 전체 구현 계획](https://github.com/edwardkim/ohmylemmings/issues/1).

## 목적과 현재 상태

[프로젝트 기획서](issue-1_rusty_lemmings.md)의 원본 호환 Rust 엔진을 작고 검증 가능한 목표로 나눕니다. 데스크톱과 웹에서 기준판의 레벨·직업·게임 규칙·사운드를 재현하는 것이 최종 목표입니다.

G00의 기준 정의를 완료했습니다. [#2](https://github.com/edwardkim/ohmylemmings/issues/2)의 원작 확보, [#3](https://github.com/edwardkim/ohmylemmings/issues/3)의 소스 고정과 [#5](https://github.com/edwardkim/ohmylemmings/issues/5)의 지원·판정 계약을 갖췄습니다. [G01-01 / #6](https://github.com/edwardkim/ohmylemmings/issues/6)에서 Rust workspace·기초 자료형·바이트 읽기와 테스트를 도입했습니다. G01은 진행, G02~G12는 대기 상태입니다. 다음 작업은 G01-02 CI·개발 검증 구성입니다.

[호환성 기준](../tech_insights/issue-5_compatibility_baseline.md)의 전체 120개 진입점·직업 8종·음악 21개·효과음 18개와 COMP-01~18을 검증 범위로 사용합니다. DOS 실행 대조·기준 추적·음원 매핑은 G05~G11의 실행 증거로 확인합니다. 미검증 항목은 통과로 계산하지 않습니다.

## 분할 원칙

1. 파싱, 지형, 시뮬레이션, 게임 세션, 플랫폼 어댑터의 책임과 입력·출력을 분리합니다.
2. 각 목표를 한 종류의 동작이나 인터페이스를 검증하는 후속 작업으로 쪼갭니다. 목표 하나에 여러 구현 PR을 연결할 수 있습니다.
3. 합성 바이너리·지형·입력 시퀀스로 코어를 검증하고, 원본 리소스와 플랫폼은 통합 목표에서 연결합니다.
4. 선행 목표가 준비되면 독립적인 모듈을 진행할 수 있습니다. 공통 인터페이스 변경은 관련 계획과 의존 작업에 반영합니다.
5. 작은 단위에서 TDD를 적용하고, 관찰 가능한 동작을 구현할 때마다 실행 가능한 결과를 남깁니다.

## 초기 실행 순서

G00 기준 정의와 G01-01을 마쳤습니다. **G01**의 개발 검증 구성을 이어 진행합니다.

1. **G00-01 기준판 식별 / #2 완료:** DOS 바이트 프로필·출처·해시로 입력을 고정했습니다. 소매판 리비전 이름은 부가 정보로 기록합니다.
2. **G00-02 레퍼런스 고정 / #3 완료:** 참고 커밋·파일·함수·역할을 고정했습니다.
3. **G00-03 완료 기준 정의 / #5 완료:** 전체 지원 목록·비교 계약·첫 레벨 시나리오·원작 버그 재현·미검증 항목의 실행 책임을 정의했습니다. 실제 실행 결과는 G05~G11에서 검증합니다.
4. **G01-01 개발 골격 / #6 완료:** [모듈 경계](issue-6_rust_workspace.md), Cargo workspace, `no_std` 라이브러리 2개와 행동 테스트·문서 예제를 도입했습니다.
5. **G01-02 개발 검증:** 포맷·린트·테스트·빌드 명령을 CI와 문서에 연결합니다.
6. **G02-01 / G04-01 독립 구현:** 첫 DAT 구간 읽기와 합성 픽셀 맵의 읽기·경계 검증을 별도 이슈로 진행합니다.

## 후속 작업 이슈의 필수 항목

- 상위 추적 이슈와 목표 ID, 예: `G02-01 DAT 구간 읽기`
- 선행 작업과 착수 조건
- 이번 작업의 범위, 입력·출력, 예외·경계 조건
- 테스트 시나리오와 관찰 가능한 완료 기준
- 관련 `plans/`, `orders/`, `tech_insights/`, `feedbacks/` 문서
- `working/` 진행 기록과 `reports/` 검증 결과

직업 구현은 직업 한 종류를 기본 작업 단위로 삼고, 공통 지형 연산과 직업 간 상호작용 검증은 각각 별도 작업으로 나눕니다. 하나의 PR에 독립적인 여러 목표가 섞이면 작업을 더 분리합니다.

## 진행 상태와 완료 처리

이 계획에서는 `대기 → 준비 → 진행 → 검증 → 완료`로 상태를 기록합니다. 선행 조건이 충족되면 준비, 구현과 문서 갱신을 시작하면 진행으로 변경합니다. 막힌 항목에는 원인과 다음 행동을 기록합니다.

1. 범위·검증 기준을 갖춘 GitHub 작업 이슈를 먼저 등록하고 생성된 번호·URL을 조회해 확인합니다.
2. `orders/yyyymmdd.md`에 이슈별 작업을 추가하고 `working/issue-<번호>_<주제>.md`에 진행 기록을 작성한 뒤 작업을 시작합니다. orders 일지와 폴더 README를 제외한 작업 문서는 이슈 번호를 이름에 포함합니다.
3. `working/`에 현재 상태와 다음 행동을 남기며 TDD로 구현합니다.
4. `reports/`에 변경 내용, 실행한 검증 명령과 결과, 남은 한계를 기록합니다.
5. 완료 기준을 충족하면 후속 이슈를 완료하고, 해당 목표의 모든 작업이 끝나면 상위 이슈의 목표를 체크합니다.
6. 변경된 기술 지식과 피드백을 문서에 반영합니다. G00~G12 전체 기준을 충족하면 상위 이슈를 완료합니다.

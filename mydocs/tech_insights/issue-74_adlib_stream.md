# G10-02 ADLIB 명령·시간·상태 계약

이슈: [#74](https://github.com/edwardkim/ohmylemmings/issues/74) · 상위 [#1](https://github.com/edwardkim/ohmylemmings/issues/1)

[자원 계약 / #72](issue-72_adlib_catalog.md)에 이어 원본 ADLIB 드라이버의 한 호출을 결정론적인 레지스터 스트림으로 옮깁니다. OPL 합성·PCM·오디오 장치·게임 이벤트 연결은 후속입니다. [출처/해시](../../assets/manifests/adlib_stream.json).

## 기준과 실행 범위

고정 [원본 목록](../../assets/manifests/dos_original.json)의 ADLIB.DAT를 기존 Rust decoder로 해제한 22125바이트 이미지 SHA-256은 `ad4f33eb383c60b5a67945987f27580fc0540e38558d4c158efe1a672db5f490`입니다. 앞 1452바이트는 x86-16 드라이버이며 이후 초기 채널 레코드·음량/주파수 표·음악/효과음 데이터가 이어집니다. 원본 실행 파일/명령 바이트는 공개 저장소에 복사하지 않습니다.

선택적 `tools/adlib_driver_reference.py`는 이 이미지의 코드를 Unicorn 2.1.4에서 직접 실행합니다. 번역한 Python 해석기를 기준으로 삼지 않습니다. CS=0x1000에 이미지를 놓고 AH 명령과 IRET 반환 프레임을 공급하며, OUT 0x388/0x389를 순서대로 기록합니다. 매 호출의 명령 실행 한도는 1,000,000개입니다. 파일 해시 확인 없이 원본 비교를 시작하지 않으며 원본 50파일을 전후 검증합니다.

ABI의 호출자 레지스터는 AX 명령을 제외하고 0, 방향 플래그는 0으로 고정합니다. 특히 DX=0이 계약입니다. IN은 0을 돌려줍니다. 장치 탐지 AH=1은 실행하지 않습니다. 이 범위는 DOS 전체 게임/IRQ/PIT/OPL 하드웨어나 소리의 실행이 아닙니다. Unicorn은 ignored 디렉터리의 별도 venv에 둔 검증 도구이며 Cargo·npm·프로젝트 런타임이나 원본 없는 CI 의존성이 아닙니다. 고정 wheel URL·크기·SHA는 manifest에 기록합니다.

## 호출과 상태

`AdlibPlayer`는 읽기 전용 `AdlibImage`를 빌리며 할당·I/O·렌더·게임 코어 변경이 없습니다. 채널 9개의 원본 20바이트 레코드와 factor/악기 기준/음악 분주기/음악 채널 수/요청 플래그/256개 레지스터 그림자/오디오 호출 번호를 명시적으로 보유합니다. `state()`는 전체 값의 복사본입니다.

| API/명령 | 원본 근거와 처리 |
| --- | --- |
| `request_music(0..20)` | AH=5 AL=0으로 playing 플래그를 비운 뒤 AH=3 AL=index+1. 다음 성공한 호출에 헤더/프로그램을 읽고 9채널 key-off와 초기화 4쓰기를 내보냄. 저장된 음높이/key-off 값은 원본처럼 유지 |
| `request_effect(0..17)` | AH=4 AL=index+1. 매 호출에 채널 8→7→6→5 순으로 빈 슬롯을 찾음. 네 슬롯이 차 있으면 마지막 요청을 보류하고 슬롯 종료 다음 호출에 시작 |
| `request_stop()` | 다음 호출에 AH=4 AL=0과 AH=2 stop/reset. 음악 key-off, reset 표의 27쓰기, 전체 채널 정지 및 대기 요청 취소. 호출 번호는 계속 증가 |
| `step(output,budget)` | 효과음 시작→음악 분주기 감소→0..8 채널 처리→분주기 재설정. 시작한 효과음도 같은 호출의 채널 처리에 다시 참여함 |

원본 주소 0x177의 상태 byte16은 0=비활성, 1=음악, 2=효과음입니다. TS enum의 정수값과 혼동하지 않습니다. byte0=음높이, 1=남은 대기, 2..3=악기 주소, 4=악기 번호, 5..6=operator 번호, 7=OPL 채널, 8..9=key-off 레지스터/값, 10..11=프로그램 주소, 12..13=현재 명령 주소, 14=음량, 15=음량 보정, 17=대기 길이, 18=전조, 19=slide입니다. 초기 악기 주소 0은 허용하며 초기 쉼표의 release 검사는 원본처럼 이미지 byte14를 읽습니다. 실제 악기 명령/음량은 검증된 16바이트 악기가 필요합니다.

## 명령과 정수

| 바이트 | 동작 |
| --- | --- |
| 00..7F | 이전 음 key-off, 음높이 계산, A0 low/B0 key-on 쓰기, 현재 주소와 대기 저장 |
| 80 | 프로그램의 다음 bar, 0 포인터이면 뒤의 프로그램 반복 주소로 이동 |
| 81 / 82 | 각각 key-off 후 slide 해제/음 유지, 대기 길이와 현재 주소 저장 |
| 83 / 85 | 각각 설정된 음악 채널 전체 정지/현재 채널만 key-off·정지 |
| 84 xx | 전조 byte 저장 |
| 86 / 87 | slide +1 / -1(255) |
| B0..BF xx | 음량 변경. 첫 operator 값에는 xx&127, 둘째에는 악기 음량+보정을 사용 |
| C1..DF | 1..31번 악기, 원본 순서의 11개 레지스터 쓰기와 전조/음량 저장 |
| E0..FF | 대기 길이 1..32 |

88..AF는 원본 8항목 점프 표 밖으로 분기하므로 오류로 거절합니다. C0의 악기 번호 0도 거절합니다. 음악 프로그램/피연산자는 전체 공유 음악 영역 2968..21731, 효과음은 22025..22125, 악기는 각 음악 영역 또는 효과음 악기 영역 21731..21989 안에서 읽습니다. 곡별 주소 정렬이나 별도 조각을 가정하지 않습니다. 활성 채널 인덱스 4 이상은 재생 종류와 관계없이 전역 효과음 악기 표를 사용합니다(원본 0x261 비교).

주파수 계산은 원본 0x349의 AL 연산을 보존합니다. `(note+transpose+4)`가 u8로 순환하며 octave/frequency-count 표를 읽습니다. 네 번의 AL shift 뒤 AX 두 배이므로 frequency-count의 하위 4비트만 주파수 표의 32바이트 단위를 선택합니다. 음역이 음수일 때는 16비트 산술 오른쪽 shift를 사용합니다. 표의 명목상 96음 범위를 넘어도 이미지 내 계산된 읽기는 허용합니다. 원본 효과음 인덱스 14가 이 경로를 사용합니다. 음높이/전조/slide/대기는 모두 원본 크기대로 순환합니다.

음량 명령은 직전 악기 명령이 DX에 남긴 operator 값을 사용합니다. 호출 시작 DX=0과 호출 내부 순서를 고정하며 별도로 채널 operator를 보정하지 않습니다. 원본 음악 인덱스 6에서 B0 사용을 확인했고 실제 원본 전체 호출 및 별도 합성 시나리오로 이 ABI 동작을 대조했습니다. 전역 operator를 보정한 미래 API를 만들 경우 호환 계약의 별도 변경이 필요합니다.

## 시간과 한도

`AdlibWrite.audio_step`는 0부터 시작하는 드라이버 호출 번호입니다. 같은 호출의 쓰기는 배열 순서가 시간 순서이며 정렬/중복 제거하지 않습니다. `AdlibState.audio_step`는 다음 호출 번호입니다. 성공한 호출만 증가하고 재시작/중단에서도 0으로 되돌리지 않습니다.

원본 0x127/0x189/0x161에서 음악 분주기를 먼저 u8 감소시키고 0인 호출만 음악을 처리한 뒤 헤더 wait_cycles로 재설정함을 확인했습니다. 0이면 256호출 주기입니다. 효과음은 이 분주기를 건너뜁니다. 각 채널의 대기도 u8 감소이며 초기 효과음은 별도의 wait=1 초기화 없이 즉시 명령을 읽습니다.

헤더 sample_rate_factor는 원본 0x4AB에서 0x5A8로 복사되지만 드라이버 내부에서는 벽시계로 환산하지 않습니다. TS의 `factor/210`은 경험적 보정이라고 명시되어 있어 원본 PIT 주기의 증거로 사용하지 않습니다. 게임 17Hz, 렌더 callback, CPU 명령 수와도 동일시하지 않습니다. G10-03 이후 원본 호출 주기/PIT와 PCM 샘플 대응을 확정해야 합니다. 이번 대조는 호출 단위 결정론을 입증합니다.

호출자가 준 명령 budget과 하드 한도 4096 중 작은 값을 9채널이 공유합니다. 명령만 순환하는 bar도 종료합니다. 범위/명령/악기/처리량/출력 용량/호출 번호 오류는 전체 재생 상태와 출력 버퍼를 보존합니다. 읽기 전용 이미지에서 검증·개수 계산을 먼저 하고 동일한 계산으로 쓰므로 임시 heap이나 고정 대형 스택 버퍼가 필요 없습니다. 충분한 출력 용량으로 같은 호출을 재시도할 수 있습니다.

## 고정 TS와의 차이

[고정 소스 목록](../../assets/manifests/reference_sources.json)의 TS commit `10c7c8b9167258503d02589cf048e2d83a43dd0a`를 함께 읽었습니다. [channel](https://github.com/tomsoftware/Lemmings.ts/blob/10c7c8b9167258503d02589cf048e2d83a43dd0a/src/game/resources/sound/sound-image-channel.ts)과 [player](https://github.com/tomsoftware/Lemmings.ts/blob/10c7c8b9167258503d02589cf048e2d83a43dd0a/src/game/resources/sound/sound-image-player.ts)을 기준으로 차이를 기록합니다.

TS는 83 종료가 TODO이고 88을 음량 명령으로 처리하지만 원본은 B0부터 음량입니다. 주파수 음역 보정의 왼쪽 shift, u8 순환이 없는 일부 합산, 재생 종류로 악기 표를 선택하는 점, 음악/효과음 스케줄과 단일 효과음 채널, 처음 한 번만 하는 timer 탐지/초기화도 원본과 다릅니다. 초기 21곡/18효과음 목록은 #72에서 실제 TS 함수와 대조했으며, 이번 전체 명령/상태의 채택 기준은 직접 실행한 원본 드라이버입니다.

## 검증과 후속

원본 없이 실행하는 Rust15/Python7 신규 테스트와 10개 합성 시나리오 877호출·1621쓰기를 연결했습니다. 합성 기준은 비공개 드라이버에 합성 표/프로그램을 공급해 생성한 전체 상태의 SHA와 순서 있는 쓰기입니다. 매 호출의 9채널/전역/플래그/256레지스터를 빠짐없이 해시하며 원본 악곡/드라이버 바이트를 포함하지 않습니다. 0분주기·8채널·모든 지원 제어 명령·음량 ABI·채널 풀·정지/재시작·음역 표 교차를 포함합니다.

원본 검사는 21곡의 모든 활성 음악 채널이 각각 두 번 반복하거나 곡이 종료할 때까지, 18효과음은 종료까지 대조합니다. 추가로 혼합/재시작 두 시나리오를 검사합니다. 매 호출의 전체 필드와 전체 레지스터 쓰기를 직접 비교하며 요약에 호출 수·쓰기 수·채널별 반복 수·명령 통계·전체 추적 SHA를 남깁니다. 결과는 [보고서](../reports/issue-74_adlib_stream.md)에 기록합니다. 다음 G10-03은 OPL 구현/라이선스와 PCM·샘플/청크 결정론 및 원본 시간 근거입니다. G10 전체는 진행 중입니다.
